# Apifox 使用与排错（商品管理系统 · Servlet + JSP）

> 配套集合：`D:\workpace\商品管理系统-Apifox接口集合.json`（Postman v2.1，直接导入）
> 8 个分组 / 52 个接口 / 92 条断言，另带 102 条返回响应定义。

---

## 一、导入之后必做的三件事

### 1. 关掉「自动跟随重定向」★ 最重要

**位置**：Apifox `设置 → 通用 → Headers → 取消勾选「自动跟随重定向」`

本项目的接口大量用 302 表达结果（登录成功、新增成功、未登录被拦……）。
Apifox 默认会**替你把 302 走完**，于是你看到的是「200 + 跳转后的页面」，
而 `Location` 和 `Set-Cookie` 两个响应头**全都被吞掉**。后果：

- 期望 302 的断言全红，但报的是页面内容对不上，**完全看不出真正原因**
- 会话变量 `adminJsid` 存不进去 → 后面所有带身份的接口连锁变成登录页

### 2. 处理「校验响应」（契约测试）

**位置**：`项目设置 → 功能设置 → 响应校验设置`（这个页面就是，路径没错）

页面分两大块：

**① 模块功能开关**（3 个，都默认亮）

| 开关 | 作用 |
|---|---|
| "接口运行"和"调试用例"里的校验响应 | 接口的「运行」页签里显不显示 |
| "单接口用例"里的校验响应 | 接口的「测试用例」里显不显示 |
| "测试步骤"里的校验响应 | 自动化测试步骤里显不显示 |

**② 校验内容**（**只有 2 项**，没有单独的 Header 项）

| 开关 | 管的是 | 建议 |
|---|---|---|
| 校验响应 **HTTP 状态码** | 实际状态码是否等于文档里定义的状态码 | **关掉** ← 那条红的来源 |
| 校验响应 **Body 的数据结构** | Body 结构是否符合文档 Schema | **关掉**（本项目返回 HTML，本来就没 Schema 可比） |

**为什么关掉状态码这项是对的**：本项目一个地址本来就有多种结果（成功 302 / 失败 200 /
越权 403），拿单一定义去比，必然误报。而**真正的状态码检查，由每个请求「测试」页签里
我写的那 92 条 `pm.test` 断言承担** —— 那些照常跑，不会漏检。所以关掉它 ≠ 放弃测试。

> 关了 Body 之后，那条「返回的数据格式不是 JSON」就再也没出现过 —— 你可以回头看，
> 现在的报错只剩「状态码不一致」一条，就是这个开关的作用。

> 三个「模块功能开关」不用动。校验内容两个都关掉后，校验响应就是个空壳，不会再报任何红。
> 想更彻底（连界面上的「校验响应」入口都不显示），再把那三个也关掉。

### 3. 重新导入时，必须选「覆盖所有字段」

**位置**：`项目设置 → 导入数据 → Postman → 上传文件 → 高级设置`

| 高级设置项 | 要选什么 | 为什么 |
|---|---|---|
| 匹配相同接口时 | **覆盖所有字段** | 选「智能合并」会**保留旧接口的响应示例**，等于白导 |
| 资源清理 | **删除** | 把新文件里已不存在的旧接口清掉，避免新旧两套并存 |

⚠️ 只导入不覆盖，会出现**新旧两套并存** —— 你点开的很可能还是旧的那套。

## 二、怎么确认自己看的是新集合

点开接口「**登录 · 管理员**」→ 右侧「**返回响应**」下拉，数一下有几条：

| 看到几条 | 说明 |
|---|---|
| **2 条**：`302 Found · 重定向` + `200 OK · 留在原页面显示错误` | ✅ 新集合，导入成功 |
| **1 条**：只有 200（body 是 JSON） | ❌ 旧集合，Apifox 补的默认定义 |
| **1 条**：只有 302 | ❌ 上一版集合（每个接口只写了一条定义） |

## 三、同一个接口本来就有好几种结果

这是本项目最容易被误判成"接口坏了"的地方：

| 场景 | 实际结果 |
|---|---|
| 带身份访问商品列表 | `200` 渲染列表页 |
| 不带身份访问商品列表 | `302` 拦去登录页 |
| `POST /login` 账号密码正确 | `302` 跳 `/mall` |
| `POST /login` 空表单 | `200` 留在登录页，显示「请输入用户名」 |

**官方规则**：*文档定义多个可能值（如 200、201），按**允许范围**校验*。
所以本集合把同一地址的多种结果**成对写进返回响应定义**（生成器里的 `fallbackOf()`）：

```js
if (code === 200) return 302; // 页面类：没带身份被拦去登录页
if (code === 302) return 200; // 跳转类：参数没过校验 → 留在原页报错
if (code === 403) return 302; // 越权类：没登录走不到权限判断，先被 302 拦走
return 0;                     // 404（图片不存在 / 路径穿越被拒）结果是稳定的，不兜底
```

## 四、报红速查表

| 你看到的红 | 是不是真失败 | 怎么办 |
|---|---|---|
| 校验响应：「实际状态码 200，定义 302」 | ❌ **假红**，代码没问题 | 关「校验响应」，或用新集合覆盖导入 |
| 校验响应：「返回的数据格式不是 JSON」 | ❌ **假红** | 同上（本项目返回的是 HTML） |
| 断言：`expected '' to include '/mall'` | ✅ **真红** | 请求没带参数 ⇒ 见下面第六节 |
| 断言：`expected '<!DOCTYPE html>...' to include '商品列表'` | ⚠️ **多半是设置问题** | 检查「自动跟随重定向」是否已关；`{{adminJsid}}` 是否为空 |
| 断言：`期望 302，实际拿到 200` | ⚠️ 先看响应体 | 拿到的是登录页 ⇒ 会话/参数没带上；是正常页面 ⇒ 关掉重定向跟随 |
| 断言：`未登录用例期望 302，却拿到 200` | ❌ **假红**，代码没问题 | Apifox 全局 Cookie 把旧会话带进来了 ⇒ 本集合已自带前置清 Cookie 脚本，重新导入即可（见第七节） |
| 断言：`Location 应当包含 /product/list` | ✅ **真失败** | 参数确实不合法，去看服务端校验逻辑 |

> **通用判据**：契约测试报红，先分清是「**接口错了**」还是「**文档错了**」。
> 分不清的时候，脱离工具用命令行打一次原始响应 ——
> **工具会带着它自己的假设，命令行不会。**

```bash
curl -i -X POST http://localhost:8080/shop/login -d "username=admin&password=123456&redirect=/mall"
```

## 五、关掉「校验响应」后还是红 —— 说明剩下的才是真红

**这两类红是两个独立系统，关掉一个不影响另一个：**

| | 谁在报 | 关「校验响应」能消掉吗 |
|---|---|---|
| 校验响应（契约测试） | 工具拿**接口文档定义**比实际响应 | ✅ 能 |
| 断言（AssertionError） | 每个请求「测试」页签里**我们写的脚本** | ❌ **不能** |

所以：**关掉开关后还红，就一定是断言真失败了**，这说明这次请求确实没按预期返回。

### 怎么一眼定位：看「Location 为空」时响应体是什么

`expected '' to include '/mall'` 这种报错的意思是「**Location 响应头是空的**」。
Location 为空有两种完全不同的原因，**用响应体里的 `<body class="xxx">` 区分**：

| Location | 响应体里是 | 真正原因 | 怎么办 |
|---|---|---|---|
| `''`（空） | `<body class="login-body">` **登录页** | 请求**没带参数**或账号密码不对 —— 根本没发生跳转，服务端按"登录失败"返回 200 | 把 Body 填回去 |
| `''`（空） | 商城页 / 列表页 | **「自动跟随重定向」没关** —— 302 被工具走完了，Location 被吞掉 | 关掉它（见第一节） |

### 最常犯的一个操作错误

**「登录 · 管理员」这条接口只能用 `admin / 123456 / /mall` 跑。**
它是"登录成功"场景，断言写死期望 302。

想测别的场景，**别去改它的 Body**，用对应那条接口：

| 想测什么 | 该跑哪条接口 | 它的请求体 |
|---|---|---|
| 登录成功 | 登录 · 管理员 | `admin` / `123456` / `/mall` |
| 普通用户登录 | 登录 · 普通用户 | `user` / `123456` / `/mall` |
| 密码错 | 登录 · 密码错误 | `admin` / `wrong-password` |
| 用户名为空 | 登录 · 用户名为空 | `username` 留空 / `123456` |

在「运行」页签里手改了参数，请求地址栏旁边会出现「**不一致**」标记 ——
看到它就说明你跑的不是接口定义里的那份请求。想还原：把 Body 重新填回上表的值。

> **一句话**：一条接口 = 一个场景。**负面场景有它自己的接口，不要去手改正面接口的参数。**

## 七、为什么「未登录」用例老是失败 —— Apifox 的自动 Cookie 管理

### 症状

跑「未登录 · 访问后台被拦截」，期望 `302`，实际拿到 `200`。
但用命令行 `curl` 打同一个地址、不带 Cookie，明明就是 302。**接口没错，是工具替你带了身份。**

### 根因

Apifox 的 **Cookie 管理**（左下角有个「**启用全局 Cookie**」开关）会把自己记着的 Cookie
自动拼进每个请求。只要之前跑过一次登录，jar 里就存着一条有效的 `JSESSIONID`：

```
Cookie 管理 → localhost → JSESSIONID=243D47A978A2C81D88CBE81A1305E6AC
            domain=localhost  path=/shop  http-only  host-only
```

于是「未登录」请求身上**挂了两个 JSESSIONID**（我们塞的无效值 + jar 里的有效值），
Tomcat 取到有效那个 → 判定已登录 → 返回 200，断言失败。

> 这条 Cookie 的「生成时间」正好是上一次跑登录的时刻 —— 看到这个时间就能对上号。

### 修法：不用你动手，脚本自己清

本集合里凡是用「无效会话」发出去的用例（`rawCookie: NO_SESSION`），生成器都会自动
挂一段前置脚本（`preClearCookie`）：

```js
// 未登录用例：先把 Apifox 自动管理的 Cookie 清掉，避免带着旧会话进来
if (pm.cookies && typeof pm.cookies.clear === 'function') {
    try { pm.cookies.clear(); } catch (e) { /* 某些版本没有这个 API，忽略 */ }
}
// 把请求头里已经拼好的 Cookie 删掉（Apifox 可能在 prerequest 之前就注入了）
pm.request.headers.remove('Cookie');
console.log('已清空 Cookie，本请求将以「未登录」身份发出');
```

三步：**清 jar → 删请求头里的 Cookie → 再塞明确的无效值**。
所以**全局 Cookie 开着还是关着，结果都一样**，不依赖用户记得去点开关。

覆盖到的 7 条接口：

| 接口 | 说明 |
|---|---|
| 未登录 · 访问后台被拦截 | 真需要"未登录"身份 |
| 未登录 · 查我的订单被拦 | 真需要"未登录"身份 |
| 商城首页（游客，不登录） | 游客身份 |
| 商城列表 · 分类 + 价格区间 + 排序 | 游客身份 |
| 商品详情 | 游客身份 |
| 图片 · 路径穿越防御 | 无会话 |
| 图片 · 文件不存在 | 无会话 |

### 想更保险（可选）

Cookie 管理弹窗点「**清空**」，或关掉「启用全局 Cookie」——都可以，但**不是必需的**。
